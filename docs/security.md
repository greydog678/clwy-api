**普通修复提交不会清除旧提交历史，也不会轮换部署环境的凭据或数据库中已有的账号密码。**

## JWT 轮换步骤

1. 盘点开发、测试、生产、容器、CI 和全部副本的 `SECRET` 来源。任何仍使用公开密钥的环境都应按已泄露处理，检查异常登录和管理员操作；避免将完整令牌或密钥写入调查日志。
2. 在受信任的私密终端或密钥管理器生成至少 32 字节密码学随机数据，推荐编码为 64 位十六进制字符串。不同环境分别生成，不复用数据库或用户密码；将结果直接保存到部署平台的密钥管理器，不经 Git 分发。README 中提供了生成命令。
3. 更新全部副本的环境变量并重启/重建进程，代码在启动时读取密钥。通过短暂停机或蓝绿切换，使流量一次性切到全部使用新密钥的副本，并撤下仍使用旧密钥的副本，避免新旧混用。
4. **不保留旧密钥兼容窗口，不等待 30 天有效期结束。** 仅凭旧签名无法区分合法和伪造令牌。切换后要求普通用户和管理员重新登录；回滚代码也必须保留新密钥，禁止恢复泄露的旧值。
5. 验证两个登录入口的新令牌可用，旧密钥令牌返回 401，普通用户仍不能访问管理接口。确认各副本行为一致；缺少或短密钥应启动失败，日志不得包含密钥、完整令牌或数据库密码。
6. 清除旧密钥在平台、旧容器、镜像、备份和 CI 中的配置/制品，检查是否复用于其他服务并分别轮换。长度校验不能证明随机性。

普通用户和管理员继续共用同一环境密钥，因此两类账号都受轮换影响。分离密钥、增加签发方/受众或缩短令牌寿命可另行设计，需考虑客户端兼容性。

## 数据库和演示账号

- 设置新的数据库应用账号密码，更新 `DB_USER`、`DB_PASSWORD`、`DB_HOST`、`DB_PORT`、`DB_NAME` 并重启全部副本。按数据库平台支持的流程协调切换，验证连接后撤销旧密码及多余权限。
- 升级前必须配置两项数据库凭据，否则应用/CLI 会拒绝加载配置。生产显式设置 `NODE_ENV=production`，确认数据库名与时区，迁移时同时使用 `--env production`。
- 重置或禁用旧种子创建的管理员及演示用户账号。修改种子不会自动更新数据库中的旧哈希；不要为轮换重跑整套种子或删除业务数据。生产不得执行演示种子。
- 本次未操作运行中的服务、密钥管理器或数据库，实际轮换由部署维护者完成。

## 如需清理 Git 历史

先轮换真实凭据，再协调维护者冻结写入、处置未合并 PR、清点分支/标签/fork 并保存受控备份。历史改写会改变提交 SHA，影响签名及协作者克隆，不能通过普通 PR 完成。

在**独立的新克隆**中安装带 `--sensitive-data-removal` 的 `git-filter-repo`（至少 2.47），可清理已确认的两个泄露文件：

```shell
git filter-repo --sensitive-data-removal --invert-paths --path .env --path config/config.json
```

这只进行本地清理，不会自动上传。先扫描所有历史路径和引用，补上文件的旧路径及其他真实密钥所在文件；检查首个改写提交、受影响引用/PR 与业务文件完整性，再由维护者审批和执行远端覆盖推送。

清理后协作者重新克隆，或按工具手册清理现有克隆，避免再次合并旧历史。fork、缓存及 PR 引用可能仍保留旧内容，按 GitHub 支持流程处理；不能保证消除外部已保存的副本。

本次仅新增普通修复提交，**未执行远端强制推送或历史改写**。

## 防止再次提交

- 只跟踪空值模板。提交前运行 `git ls-files .env`（应无输出），用 `git check-ignore -v --no-index .env .env.production` 验证忽略规则，避免强制添加环境文件。
- 不使用硬编码密钥回退；运行时从密钥管理器注入，不在构建阶段写入镜像。
- 根据仓库支持情况启用 secret scanning/push protection，并补充针对通用应用密钥的本地或 CI 检查；平台扫描未必识别所有自定义 `SECRET`。
- 运行安全测试并保留 `package-lock.json`。已被跟踪的 `node_modules` 和编辑器文件未在本次批量删除，新增规则仅阻止新增未跟踪文件，已有目录取消跟踪可单独安排。
